# Как ноды находят друг друга в Asty (после правок)

## Контекст

Asty — оркестратор для NATS-кластера. На каждой ноде Asty-агент сам запускает локальный `nats-server` (NATS-брокер), а несколько таких брокеров объединяются в кластер. Чтобы кластер собрался, новому брокеру нужно знать хотя бы один IP-адрес уже работающего брокера — это называется **seed**. После соединения они сами обмениваются метаданными и становятся единым целым.

Поверх NATS Asty держит свою базу `JetStream KV` (key-value хранилище с репликацией). Туда каждый агент пишет запись `node.<id>` со своими параметрами (IP, имя, ресурсы и т.д.) — это и есть **список живых нод** с точки зрения Asty. Другие компоненты (планировщик, дашборд) читают именно его.

## Как было раньше (через DNS)

В старой схеме у кластера было одно общее доменное имя, например `cluster.example.com`. У него N A-записей — по одной на каждую живую ноду. Когда оператор добавлял ноду, он просто прописывал её IP в DNS.

Каждый агент **раз в 5 секунд** делал `LookupIP(домен)` и получал полный список IP. Если набор изменился — перерисовывал `nats.conf` и просил свой `nats-server` подхватить новые `cluster.routes` (либо через сигнал `SIGHUP`, либо через полный рестарт, если переходил из режима single-node в clustered).

Минусы:
- **Опрос (polling)**: лаг до 5 секунд на каждой ноде.
- **Внешняя зависимость**: нужен DNS, синхронизация записей, в dev-окружении — отдельный костыль с `/etc/hosts`.

## Что изменилось

DNS убрали полностью. Вместо него — три механизма, работающих вместе.

### 1. Cold bootstrap: `A_NATS_SEED`

При деплое **новой** ноды оператор передаёт ей через переменную окружения `A_NATS_SEED` IP **одной уже живой** ноды кластера. Например:
```
A_NATS_SEED=10.0.0.1
```

Агент при старте кладёт этот IP в свой in-memory peer-set, затем рендерит `nats.conf` с `cluster.routes = ["nats-route://10.0.0.1:6222"]` и запускает локальный `nats-server`. Тот соединяется с указанным узлом и через NATS-gossip автоматически узнаёт об остальных.

Если переменная пуста — это **самая первая нода** кластера, она запускается в standalone-режиме без блока `cluster {}` (NATS не принимает пустой блок при старте).

### 2. SSH + CLI: уведомление живых нод о новой

Проблема: первая нода standalone — у неё **порт 6222 закрыт** (нет блока `cluster {}` в конфиге). Если просто запустить вторую ноду с `A_NATS_SEED=<ip-первой>`, она будет вечно стучаться в закрытый порт.

Решение: **до старта** новой ноды надо сообщить какой-то живой ноде «жди соединение с такого-то IP». Делается это так:

С новой ноды, по SSH в живую ноду, запускается одна команда:
```
ssh asty@10.0.0.1 "asty admin add-peer"
```

На стороне живой ноды этот процесс:
1. Берёт IP клиента из переменной `$SSH_CLIENT` (её ставит сам `sshd` — мы не передаём IP параметром).
2. Подключается к **локальному** `nats-server` (через `127.0.0.1:4222`) с теми же кредами, что использует агент.
3. Публикует на NATS специальную команду `CmdAddPeer` с этим IP.

Безопасность: никаких сетевых эндпоинтов наружу нет. Доступ ограничен SSH-ключом, в `authorized_keys` можно прописать `command="asty admin add-peer"` — этот ключ сможет запустить ровно одну команду, ничего больше.

### 3. Обработка команды `CmdAddPeer` и broadcast

Агент, получивший команду, выполняет три действия:

1. **Добавляет IP** в свой in-memory bootstrap-peer-set (`a.peers.bootstrap`).
2. **Сигнализирует супервизору** `nats-server`: пора обновить `nats.conf`. Супервизор сравнивает старый и новый файл:
   - Если конфиг **никогда не имел** блока `cluster {}` (была standalone-нода) → полный рестарт `nats-server`. Только так он узнает, что теперь надо открывать порт 6222 и слушать routes.
   - Если блок уже был → SIGHUP, NATS на лету перечитает routes без потери соединений.
3. **Публикует уведомление** на NATS-subject `asty.v1.cluster.peer_announce` с тем же IP.

Этот broadcast — замена DNS-поллинга. На subject подписан **каждый** агент кластера. Когда нода 1 обработала `add-peer` от ноды 3 и опубликовала broadcast — нода 2 (и любая другая) получает уведомление и делает то же самое локально: кладёт 127.0.0.3 в свой bootstrap-set, SIGHUP'ит свой `nats-server`.

В итоге за миллисекунды **все живые ноды** знают о новой и устанавливают к ней прямые route'ы — получается полная сетка (full mesh), как было через DNS, но event-driven, без 5-секундного лага.

### 4. Что делает новая нода после старта

Когда у нового агента поднялся `nats-server` и она подключилась к локальному NATS:
- Подписывается на свой subject команд (`asty.v1.agent.<id>.cmd.*`).
- Подписывается на тот же `asty.v1.cluster.peer_announce` — будет узнавать о будущих новых нодах.
- Начинает раз в 5 секунд писать heartbeat: свою запись `node.<id>` в KV-бакет `asty-cluster`. Это и есть момент, когда нода становится **видна Asty** — в дашборде, планировщике и т.д.
- Запускает `watchNATSPeers` — подписывается на изменения `node.<id>` в KV. Это **постоянный** источник peer-IP'ов после bootstrap: KV — авторитетная база для всего Asty.

### 5. Поддержание сетки в актуальном виде через KV

После того как новая нода зарегистрировалась в KV, все агенты получают это событие через `WatchNodes`. Они добавляют запись `nodeID → IP` уже в **рабочий** peer-set (`a.peers.byNode`), а не bootstrap. При следующем рендере `nats.conf` рабочий и bootstrap-наборы объединяются, дубликаты по IP схлопываются.

То есть bootstrap-набор — это «временное знание перед первым успешным присоединением», а `byNode` — «устойчивое знание из KV». Они мирно сосуществуют.

При выходе ноды из кластера (грейсфул-шатдаун) её запись `node.<id>` удаляется из KV — `WatchNodes` выдаёт событие удаления, peer убирается из `byNode`, SIGHUP, кластер сжимается.

### 6. Replicas-апгрейд KV-бакетов

Дополнительная сложность: KV-бакеты в JetStream имеют параметр `replicas`. Когда нода 1 создавала бакеты в одиночку, у них replicas=1. Когда подключилась нода 2 — leader (тот узел, что выиграл выборы лидерства) повысил replicas до 2, чтобы данные физически легли на оба узла.

Этот апгрейд делает `streamreplicas.go` (только на лидере). Он подписан на два сигнала:

- `WatchNodes` (KV) — но KV-уведомление приходит ПОСЛЕ того, как новая нода успешно зарегистрировалась. А зарегистрироваться она может только когда бакет на ней реплицирован. Замкнутый круг.
- `DiscoveredServersHandler` — это callback NATS-клиента, срабатывает в момент, когда локальный `nats-server` лидера в gossip узнал о новом брокере. Это происходит **раньше**, чем новая нода успевает записать что-то в KV.

После broadcast'а из пункта 3 все NATS-серверы узнают о новом и устанавливают прямые route'ы. NATS лидера через gossip получает информацию — срабатывает `DiscoveredServersHandler` — лидер делает `UpdateStream` и поднимает replicas до 3. Бакеты становятся физически доступны на новой ноде, она успешно читает `asty-cluster`, регистрируется через heartbeat — круг замкнулся в правильную сторону.

### 7. Удаление ноды — зеркало добавления

Добавление и удаление идут по ОДНОМУ механизму, просто в разные стороны:

- **Реплики.** Тот же reconcile (`reconcileStreamReplicas` на лидере) на
  приход ноды ПОВЫШАЕТ число реплик через `UpdateStream`, на уход —
  ПОНИЖАЕТ его до `min(потолок, размер кластера)`. Целевой размер берётся
  из RAFT-метагруппы JetStream (`clusterSize` через self-JSZ в
  `server/kv.go`), а НЕ из gossip: `DiscoveredServersHandler` — только
  ранний сигнал, по которому reconcile запускается; как счётчик gossip
  непригоден, потому что это накопительный набор и после коллапса он
  устаревает. RAFT-метагруппа — единственный авторитетный источник
  членства у NATS.
- **Маршрутная сетка.** Её ведёт тот же `watchNATSPeers` (KV `WatchNodes`):
  `upsert` добавляет route на приход, `remove` убирает на уход — оба
  через SIGHUP того же супервизора.

Единственная асимметрия продиктована самим NATS. Брокер вступает в
метагруппу JetStream АВТОМАТИЧЕСКИ, как только подключился по cluster
routes, — на добавлении ничего явного делать не надо. А ушедшую ноду
NATS из метагруппы сам НЕ убирает: она висит offline-пиром, пока кто-то
явно не пошлёт `$JS.API.SERVER.REMOVE` (в документации NATS это
«destructive operation»). Поэтому на стороне удаления есть явный «жнец»
мёртвых peer'ов (`server/deadpeers.go`), а осиротевшую реплику переселяет
`$JS.API.STREAM.PEER.REMOVE` (`server/streamplacement.go`). На стороне
добавления симметричного «явного шага» нет — за нас его делает NATS.

Полный разбор смерти ноды, кворума и схлопывания N→1 — в `REPLICAS_KV.md`
(§8–10).

## Полный сценарий: 1 → 2 → 3 ноды

**Шаг 1.** Запуск ноды 1 (`A_NATS_SEED` не задана).
- Агент рендерит `nats.conf` без блока `cluster {}`.
- `nats-server` стартует в standalone-режиме. Порт 6222 закрыт.
- Агент подключается к NATS, регистрируется в KV. Дашборд показывает 1 ноду.

**Шаг 2.** Добавление ноды 2 (с `A_NATS_SEED=10.0.0.1`).

Перед запуском процесса агента, скрипт (или cloud-init) делает SSH:
```
ssh asty@10.0.0.1 "asty admin add-peer"
```
- На ноде 1 эта CLI извлекает `10.0.0.2` из `$SSH_CLIENT`, публикует `CmdAddPeer{IP: "10.0.0.2"}` локальному агенту.
- Агент ноды 1 кладёт `10.0.0.2` в bootstrap-set, сигнализирует супервизору.
- Супервизор видит: старый конфиг без `cluster {}`, новый — с `cluster {}` и routes=[10.0.0.2] → **полный рестарт** `nats-server`. Теперь порт 6222 открыт.
- Агент ноды 1 публикует broadcast `peer_announce{IP: "10.0.0.2"}`. Других нод пока нет — broadcast уходит в пустоту, это безопасно.

Затем стартует агент на ноде 2:
- Из `A_NATS_SEED=10.0.0.1` кладёт `10.0.0.1` в bootstrap-set.
- Рендерит `nats.conf` с routes=[10.0.0.1], запускает свой `nats-server`.
- `nats-server` подключается к 10.0.0.1:6222 (порт уже открыт), вступает в JetStream meta-кластер. Лидер JS — нода 1 (или нода 2 — переизберётся).
- Агент ноды 2 подключается к локальному NATS, регистрируется в KV.
- На ноде 1 `WatchNodes` видит появление ноды 2 → добавляет в `byNode` → SIGHUP `nats-server` (он уже знает о ноде 2, но конфиг обновится для consistency).
- Лидер Asty (положим, нода 2) через `DiscoveredServersHandler` узнаёт о расширении кластера → апгрейдит KV-бакеты с replicas=1 до 2.

**Шаг 3.** Добавление ноды 3 (с `A_NATS_SEED=10.0.0.1`).

SSH на ноду 1:
```
ssh asty@10.0.0.1 "asty admin add-peer"
```
- На ноде 1 CLI публикует `CmdAddPeer{IP: "10.0.0.3"}`.
- Агент ноды 1 кладёт `10.0.0.3` в bootstrap-set, сигнал супервизору. Старый и новый конфиг — оба с `cluster {}` → **SIGHUP** (быстрый горячий релоад, без рестарта).
- Агент ноды 1 публикует broadcast.
- **Нода 2** получает broadcast → кладёт `10.0.0.3` в bootstrap-set → SIGHUP своего `nats-server`. Теперь и нода 2 готова принять соединение от ноды 3.

Затем стартует агент на ноде 3:
- Кладёт `10.0.0.1` в bootstrap-set из `A_NATS_SEED`.
- Запускает `nats-server` с routes=[10.0.0.1].
- `nats-server` подключается к 10.0.0.1, через gossip узнаёт о 10.0.0.2 → устанавливает прямой route к ней. Сетка полная.
- Агент подключается к локальному NATS, ищет бакет `asty-cluster`. На этот момент бакет ещё с replicas=2.
- Лидер Asty через `DiscoveredServersHandler` узнаёт о ноде 3 → апгрейдит replicas с 2 до 3. JetStream реплицирует данные на ноду 3.
- Агент ноды 3 успешно читает бакет, регистрируется через heartbeat. Дашборд показывает 3 ноды.

## Где какой код живёт

- **Cold bootstrap из env**: `asty/internal/agent/agent.go` (заполнение bootstrap-set в `New()`), `asty/internal/agent/natssup.go` (`renderNATSConf` использует `a.peers.snapshot()`).
- **CLI**: `asty/cmd/main.go` (`runAdminAddPeer` — извлечение `$SSH_CLIENT`, NATS-публикация).
- **Команда CmdAddPeer**: `asty/internal/core/types/commands.go` (тип), `asty/internal/agent/commands.go` (handler).
- **Broadcast peer_announce**: subject в `core/types/commands.go`, publish в handler'е `handleAddPeerCommand`, subscribe в `subscribePeerAnnounce` (`agent/commands.go`), вызов подписки в `agent/start.go`.
- **Watch KV node.***: `asty/internal/agent/natspeers.go` (`watchNATSPeers`).
- **Supervisor `nats-server`**: `asty/internal/agent/natswatch.go` (решение SIGHUP vs cold restart по факту наличия блока `cluster {}` в старом конфиге).
- **Replicas-апгрейд по gossip**: `asty/internal/server/streamreplicas.go` (handler `gossipChanged`), `asty/internal/server/nats.go` (подключение `DiscoveredServersHandler` к NATS-connection).

## Что важно понимать

- **Bootstrap — это передача знания "куда стучаться в первый раз"**. После того как нода подключилась к NATS-кластеру, дальнейшее обновление списка пиров уже идёт через NATS (broadcast + KV).
- **SSH-канал нужен ровно один раз** — чтобы пробудить standalone-ноду или сообщить кластеру о новой. Дальше всё через NATS.
- **Никаких поллингов**: ни DNS, ни тикеров «проверим список пиров каждые N секунд». Только событийные сигналы: `WatchNodes` (KV), `peer_announce` (pub/sub), `DiscoveredServersHandler` (NATS).
- **Конфиг `nats.conf` хранится на диске**: даже если агент перезапустится, `nats-server` поднимется со всеми последними peer'ами в routes. Это работает потому, что `renderNATSConf` всегда читает из единого `a.peers.snapshot()`, куда сходятся все источники.
