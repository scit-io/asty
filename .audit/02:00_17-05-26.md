## 0. Summary

1. Pipeline carries **two incompatible wire shapes** across two NATS subject trees: zerolog JSON on `asty.v1.server.logs` (server self-logs) and `asty.v1.agent.<id>.logs.agent` (agent self-logs), plus `LineFrame{line,timestamp}` on `asty.v1.agent.<id>.logs.<svc>` (per-service stdout). Inside the LineFrame, the `line` body is whatever the child process printed — and for demo services that means raw `zerolog.ConsoleWriter` text with ANSI escapes, which is the source of the user-reported artefact. UI rendering boils down to "stringify and show".
2. **Two different server-side string formatters** collapse the JSON into "[time] [level] message …" — one for live SSE, one for the in-memory history buffer. They use different time formats (RFC3339 vs Unix decimal), and one of them silently drops the extras map. Same data, two displays.
3. **ANSI colour codes leak from demo services through to the browser**. xauth/xhttp/xws use `zerolog.ConsoleWriter` writing to stderr; process stdio is redirected to a file; the agent tails the file as opaque text and ships it forward. The `␛[90m1:47AM␛[0m ␛[32mINF␛[0m xauth started` artefact comes from there.
4. **Structured fields are non-recoverable at the UI**. The Extras map (`{node_id, ...}`) is either dropped (history) or `json.Marshal`-concatenated into the line (live). Either way the browser sees a string blob and would need a regex to find the level, the time, or any key.
5. Two near-identical types (`LineFrame`, `LogLine`) and a redundant `time`/`timestamp` field pair are artefacts of the format mismatch — they collapse once the wire shape is unified.
6. Recommended target: **one canonical structured `LogEntry{time, level, msg, fields}` from emitter to renderer**, no string baking server-side. Demo services switch to JSON output; agent forwards verbatim; server-side formatters delete; UI parses an object and renders cells.

This is one architectural fix with cascading deletions — not many small ones.

## 1. Critical

### 1.1 ANSI escapes leak from demo services to the dashboard `[+]`

`demo/cmd/xauth/main.go:20`, `demo/cmd/xhttp/main.go:24`,
`demo/cmd/xws/main.go:21` all do:

```go
log.Logger = log.Output(zerolog.ConsoleWriter{Out: os.Stderr})
```

`ConsoleWriter` is a TTY decorator — it injects ANSI colour codes and
formats time as `3:04PM`. The service's stdout+stderr are wired to the
agent-managed log file by `features/execution/process/process.go:122-126`
(`p.cmd.Stdout = p.logFile`). The agent's `streamProcessLogs`
(`asty/internal/agent/logstream.go:55-58`) then reads the file
line-by-line and JSON-marshals each line into
`{"line": "<raw stdout>", "timestamp": ...}` for NATS publish on
`asty.v1.agent.<id>.logs.<svc>`. The string body keeps the ANSI bytes
intact, JSON-escapes them as `[...`, and the SPA renders the
result verbatim.

**Action:** demo services emit JSON, not ConsoleWriter text. Replace
the three `log.Output(zerolog.ConsoleWriter{...})` lines with the
zerolog default (`log.Logger.Level(...)` only; the package default
writes JSON to `os.Stderr`). Stderr-via-terminal users can re-pipe
through `zerolog/journald` or `jq` themselves.

Rule cite: `.claude/coding-rules/clarity.md` — "write so non-developers
can follow"; today's output fails that for anyone reading
`/nodes/{id}/allocations/{id}/logs`.

### 1.2 Two divergent server-side string formatters for the same payload `[ ]`

`asty/internal/features/api/logs.go:47-68` — live SSE path:

```go
timeStr := time.Now().Format(time.RFC3339)
if ts > 0 { timeStr = time.Unix(ts, 0).Format(time.RFC3339) }
line := fmt.Sprintf("[%s] [%s] %s", timeStr, e.Level, e.Message)
if len(e.Extras) > 0 {
    if b, err := json.Marshal(e.Extras); err == nil {
        line += " " + string(b)
    }
}
```

`asty/internal/server/logbuffer.go:59-64` — history-buffer path:

```go
timeStr := ""
if e.Timestamp > 0 {
    timeStr = fmt.Sprintf("%d", e.Timestamp)
}
line := fmt.Sprintf("[%s] [%s] %s", timeStr, e.Level, e.Message)
```

Same input → two different strings. Live shows RFC3339 and Extras
JSON; history shows raw Unix seconds and drops Extras entirely. The
UI reads them through one component (`LogsView`), so a user sees a
discontinuity at the moment the buffered prefix ends and the live tail
begins. This is the source of the user-reported "[2026-05-17T01:57:44+04:00] [debug] heartbeat sent {…}" shape — the `formatLogEntry`
path is the one currently feeding the browser.

**Action:** delete both formatters; emit canonical structured JSON
on every path. See plan §5 phase B.

Rule cite: `.claude/coding-rules/code-idioms.md` — "Helpers when the
same shape repeats 3+ times". Here the inverse — the same operation
must not have two divergent implementations.

### 1.3 Structured data lossy-flattened to a string at the API boundary `[ ]`

The pipeline is JSON-native end-to-end (zerolog event → NATS bytes →
`DecodeZerologEntry` → typed `ZerologEntry`) right until
`api/logs.go:97`:

```go
line := formatLogEntry(entry)
data, _ := json.Marshal(logs.LineFrame{Line: line, Timestamp: entry.Timestamp})
fmt.Fprintf(w, "data: %s\n\n", data)
```

The fully-typed `entry.Level`, `entry.Message`, `entry.Extras` are
collapsed back into a single string before the SSE frame leaves the
server. The browser then has no way to:

- colour the level (it's a substring at a known but format-dependent
  offset),
- format the timestamp in the user's locale (already RFC3339-fixed),
- show structured fields as a key/value panel (Extras is a
  JSON-string-tail that the UI would need to parse with a regex).

This is the core of the user's complaint.

**Action:** SSE emits the typed `LogEntry` object directly. UI receives
`{time, level, msg, fields}`, decides display. Phase B in plan.

## 2. High

### 2.1 Three distinct payload shapes on `asty.v1.*.logs.*` `[ ]`

The agent and server publish zerolog JSON
(`{"level":"info","time":...,"timestamp":...,"message":"...","key":"val"}`).
`streamProcessLogs` (asty/internal/agent/logstream.go:55-58) publishes
`{"line":"<raw stdout>","timestamp":...}` on the same wildcard tree.
`DecodeZerologEntry` parses both kinds because LineFrame happens to be
a subset of the zerolog shape (no `level`, no `message`, an unknown
`line` extra → trips `AsLineFrame()` recovery at entry.go:75-88).

This recovery is clever but fragile: a real zerolog event that happens
to have a single extra named `line` would be misclassified. More
importantly, it locks the system into supporting two formats forever.

**Action:** post-unification only one shape exists, `AsLineFrame()` and
its callers go away (entry.go:75, api/logs.go:48-50, server/logbuffer.go:55-58).
A high-priority candidate for deletion.

### 2.2 `LineFrame` and `LogLine` are near-duplicate types `[ ]`

`asty/internal/features/observability/logs/entry.go:13` — wire shape
between agent and SSE:

```go
type LineFrame struct {
    Line      string `json:"line"`
    Timestamp int64  `json:"timestamp"`
}
```

`asty/internal/features/observability/logs/buffer.go:10` — buffered
entry shape:

```go
type LogLine struct {
    Timestamp int64  `json:"ts"`
    Level     string `json:"level,omitempty"`
    Line      string `json:"line"`
}
```

Same data, two field orders, two JSON tags (`timestamp` vs `ts`). They
exist because the format wasn't decided when each was written.
`LogLine.Level` is set by `makeLogAppender` but never read — see 3.1.

**Action:** collapse to one `LogEntry{time, level, msg, fields}` once
the format is unified. Both types delete.

### 2.3 `time` and `timestamp` carry the same Unix second `[ ]`

`asty/cmd/main.go:25-26`:

```go
zerolog.TimeFieldFormat = zerolog.TimeFormatUnix
log.Logger = log.Output(zerolog.ConsoleWriter{Out: os.Stderr}).Hook(logs.TimestampHook{})
```

`TimestampHook` (timestamp_hook.go:20) injects
`Int64("timestamp", time.Now().Unix())`. zerolog's package-default
`log.Logger` already emits `time` via the implicit `.Timestamp()` in
the global logger init, and with `TimeFormatUnix` set the value is
the same Unix-second integer. Each event therefore carries two
identical numeric fields under two names. The decoder reads both
(entry.go:54-59) but only `Timestamp` is used downstream; `Time` is
documented as "kept for completeness" at entry.go:25-26.

**Action:** drop the hook (and the `Time` field), use `time` for the
canonical timestamp. If millisecond precision is wanted, switch the
global to `TimeFormatUnixMs` instead of compensating with a hook.

## 3. Medium

### 3.1 `LogLine.Level` is dead by the time the buffer stores it `[ ]`

`server/logbuffer.go:64`:

```go
line := fmt.Sprintf("[%s] [%s] %s", timeStr, e.Level, e.Message)
s.logBuffer.Append(source, logs.LogLine{Timestamp: e.Timestamp, Level: e.Level, Line: line})
```

The level is baked into `Line` and *also* set on `LogLine.Level`. No
reader of the buffer (`api/logs_cluster.go:18`, `api/logs_node.go:23`,
`api/logs.go:113-116`) accesses `.Level` — they read `.Line` and `.Timestamp`.

**Action:** falls out of the format unification — when the buffer
stores a `LogEntry`, `Level` becomes a first-class field that the UI
reads. Today's redundant storage goes away.

### 3.2 `formatLogEntry` fixes timestamp display to RFC3339 server-side `[ ]`

`api/logs.go:56-58`:

```go
timeStr := time.Now().Format(time.RFC3339)
if ts > 0 { timeStr = time.Unix(ts, 0).Format(time.RFC3339) }
```

The browser is the place that knows the user's locale and whether
relative time is wanted. Pre-baking the format server-side denies the
UI that choice.

**Action:** UI receives Unix-millis on the wire; renders with
`Intl.DateTimeFormat` or `Intl.RelativeTimeFormat`.

### 3.3 `streamFromNATS`'s `fallthroughOnParse` is a tell `[ ]`

`api/logs.go:86-108` accepts a `fallthroughOnParse bool` flag. The
only call site that sets it to `true` is `logs_allocation.go:39` —
because allocation logs are LineFrames, and `DecodeZerologEntry`
"succeeds" on them via the AsLineFrame trick rather than fast-failing.
The flag is essentially "this stream is the not-zerolog one".

**Action:** once 2.1 lands the flag has nothing to discriminate; delete
the parameter, both call sites simplify.

### 3.4 Demo services don't honour `A_LOG_LEVEL` `[ ]`

`asty/internal/agent/agent.go:102` exports `A_LOG_LEVEL` so child
processes inherit it, but none of `demo/cmd/{xauth,xhttp,xws}/main.go`
read it (no `os.Getenv("A_LOG_LEVEL")`, no `zerolog.SetGlobalLevel`).
Debug logs from a noisy service can't be silenced via the agent
config.

**Action:** in each demo main, after the writer setup, add the
standard:

```go
if lvl, err := zerolog.ParseLevel(os.Getenv("A_LOG_LEVEL")); err == nil {
    zerolog.SetGlobalLevel(lvl)
}
```

(One named helper in `demo/internal/common/` would do it once for all
three; demo intentionally has no shared SDK per project policy, so
copy-paste is acceptable.)

### 3.6 Dashboard log styling must work in light and dark themes `[ ]`

Once the wire shape is unified and the UI receives structured entries,
the log view should render them with explicit styling — colour-coded
level badges, muted timestamp, monospace message, expandable fields
panel — and the colours must read well under both light and dark
themes the app already supports. Use the existing Tailwind tokens
(`muted`, `foreground`, `destructive`, etc.) rather than hard-coded
hex so the theme switch flows through automatically.

**Action:** part of frontend phase; see plan §5.C.2/C.4.

### 3.5 SSE round-trips JSON → string → JSON `[ ]`

`api/logs.go:88-99` Unmarshals the zerolog JSON into a typed entry,
runs `formatLogEntry` to turn it back into a string, then `json.Marshal`s
a one-field `LineFrame{Line: …}` to emit it on the wire. The cleanest
form is "forward the raw bytes" — but only after 2.1 settles on a
single canonical shape that doesn't need re-formatting per consumer.

**Action:** see plan §5.B.

## 5. Refactor plan

Three phases. The architectural fix is upstream; downstream code
deletions cascade from it.

### Phase A — pick the canonical shape and source it consistently

**A.1** Decide the canonical `LogEntry` shape. Recommendation:

```go
type LogEntry struct {
    Time    int64             `json:"t"`           // Unix millis
    Level   string            `json:"l,omitempty"` // "debug","info","warn","error","fatal"
    Message string            `json:"m"`
    Fields  map[string]any    `json:"f,omitempty"`
}
```

(Short keys keep wire size sane; zerolog can emit these directly via
`TimeFieldFormat = TimeFormatUnixMs`, `TimestampFieldName = "t"`,
`LevelFieldName = "l"`, `MessageFieldName = "m"`.) `[ ]`

**A.2** Drop `ConsoleWriter` from demo services; set the zerolog field
names per A.1; let stderr carry JSON. `[ ]`

**A.3** `TimestampHook` deletes; rely on zerolog's built-in
`.Timestamp()` (already present in the default global logger). `[ ]`

**A.4** `streamProcessLogs` (asty/internal/agent/logstream.go) — when
a service stdout line is already valid JSON-with-Time-Level-Message,
publish verbatim. Lines that aren't (panic dumps, raw `fmt.Println`
inside a service) get wrapped into the canonical shape with
`{l:"info", m: rawLine, t: now}` so the consumer never sees two
formats. `[ ]`

### Phase B — collapse server-side formatters

**B.1** Delete `formatLogEntry` in `api/logs.go`. Delete the formatter
inside `makeLogAppender` in `server/logbuffer.go`. The buffer stores
canonical `LogEntry`; SSE emits canonical JSON; agent's snapshot RPC
(`agent/commands.go:159` → `LogsResponse.Logs`) returns
`[]LogEntry` instead of `[]string`. `[ ]`

**B.2** Merge `LineFrame` and `LogLine` into the new `LogEntry` from
A.1. Delete `AsLineFrame` and the recovery branch in
`DecodeZerologEntry`. `[ ]`

**B.3** Drop the `fallthroughOnParse` argument to `streamFromNATS`
(api/logs.go:86, logs_allocation.go:39, logs_cluster.go:33,
logs_node.go:39). `[ ]`

**B.4** Update `types.LogsResponse.Logs` to `[]LogEntry`. Wire format
migration is local because the only consumer is `api/logs_allocation.go`. `[ ]`

### Phase C — frontend

**C.1** Add `interface LogEntry { t: number; l?: string; m: string; f?: Record<string, unknown> }`
to `asty/web/src/types/index.ts`. Replace `logs: string[]` with
`logs: LogEntry[]`. `[ ]`

**C.2** Refactor `LogsView` to render rows of `(time, level, message, fields)`:

- time cell: `Intl.DateTimeFormat` (locale-aware), tooltip with full RFC3339
- level cell: coloured badge using existing Tailwind tokens (debug=muted, info=foreground, warn=yellow, error=destructive)
- message cell: monospace truncated, expands on click
- fields cell: collapsed pill `n fields` that pops a small key/value panel

Maintain the auto-scroll + retry behaviour already in place
(logs-view.tsx:33-70). `[ ]`

**C.4** Verify colour palette in both light and dark themes. Use only
Tailwind theme tokens (`muted-foreground`, `destructive`, `primary`,
…) so the theme switch carries them. Spot-check contrast ratios for
the level badges — debug/info are the easiest to lose under one
theme or the other. `[ ]`

**C.3** Drop the `JSON.parse` fallback `data.line ?? JSON.stringify(data)`
in `logs-view.tsx:43` once C.1 ships. `[ ]`

### Phase D — clean-up

**D.1** Remove `A_LOG_LEVEL` no-op in demo services (3.4). `[ ]`

**D.2** Move the three repeated `zerolog.TimeFieldFormat = ...` /
`log.Output(...)` blocks into a `demo/internal/common/log.go` helper
exposing `InitJSONLogger()` (acceptable copy-paste under demo's
no-shared-SDK rule; this is service bootstrap, not domain code). Or
leave inline — it's three lines each and the rule wins. `[ ]`

**D.3** Update `feedback_*` memory if any rule emerged: e.g. "logs are
always structured JSON end-to-end; never bake a display string
server-side". `[ ]`

## 8. What's good (anchor)

- `NATSWriter.Write` is genuinely zero-copy: zerolog emits JSON, the
  writer publishes the bytes to NATS verbatim. The `io.MultiWriter`
  composition with stderr is idiomatic.
- `DecodeZerologEntry` correctly separates known fields from `Extras`
  using `map[string]json.RawMessage`. The shape is right; only the
  downstream collapse to string is wrong.
- `LogsView` reconnect-with-backoff (`logs-view.tsx:55-61`) is solid
  and survives both server restarts and network blips.
- Ring buffer + `GetLast(n)` is a clean, bounded-memory history
  store. No change needed at the storage layer.
- Per-process log file with optional rotation
  (`features/execution/process/logs.go`) is a sound foundation for
  multi-tenant log capture. JSONL doesn't change that.
