# Audit — communication efficiency (text vs bytes)

**Scope:** asty orchestrator package (`asty/internal/**`, ~13.5k LOC of 17.3k total Go).
**Branch:** `main` @ `5ed5217`.
**Focus:** every serialization site between processes — KV state, NATS pub/sub, NATS request/reply, SSE, HTTP. Where text (JSON) is mandatory and where bytes (a binary codec) would be a real win.

**Markers:** `[ ]` not started · `[~]` in progress · `[+]` done.

---

## 0. Top summary

- **64 JSON sites in asty/internal/** (excluding tests). Zero binary codecs anywhere. Direct `encoding/json` calls scattered across 14 files. No abstraction layer to swap implementation.
- **Three serialization profiles are conflated under one format:**
  1. *Live machine-to-machine pub/sub* (commands, logs, drain events, gateway metrics) — high frequency, byte budget matters under load, nobody reads with eyes.
  2. *Operator-readable state of record* (NodeInfo, allocations, cooldowns, scale, leader info) — kept in KV explicitly so operators can `nats kv get` it.
  3. *Browser-facing surfaces* (SSE, `/api/v1/*` JSON, `/metrics` Prometheus text) — text-mandatory by protocol or audience; off-limits to binary.

  Each profile wants a different trade-off, but they all share `encoding/json` and the same call sites — currently no way to optimise one without touching the others.
- **Hot-path waste, format-independent:** `observability/logs/nats_writer.go:25` unmarshals zerolog's already-finished JSON into a `map[string]any` and remarshals it on every log line just to inject `timestamp`. `server/logbuffer.go:50` and `api/logs.go:96` do the same `map[string]any` reparse on the consumer side. These are CPU bills the system pays per log line regardless of which codec backs it.
- **`commands.go` (core/types) wraps every command in a two-step marshal:** payload first, then `Command{Type, Data: json.RawMessage}` around it. Uses `json.RawMessage` so no double-escaping, but the outer Marshal still re-walks the payload bytes. Six call sites, all collapsible to a single pass.
- **Heartbeat and process-metrics are KV writes, not NATS publishes** (`agent/heartbeat.go:37` → `clusterState.UpdateNode` → `state/nodes.go:38` `bucket.Put`). So "binary on the wire for heartbeat" is the same decision as "binary in KV." There is no in-between unless heartbeat is decoupled from KV persistence.
- **Where binary actually pays off** (in order of bytes-saved × frequency):
  1. process log lines (`agent/logstream.go:54`, every line from every running process on every node)
  2. server log lines (zerolog hook publishing to `asty.v1.server.logs`)
  3. heartbeat NodeInfo (~600 B every 5 s per node, only if KV is included)
  4. allocation records (~400 B every 10 s per running process, only if KV is included)
  5. drain progress, gateway metrics fan-out (low frequency, but free wins once codec exists)
- **Where binary is a category error and must stay JSON:** SSE (`/api/v1/*?Accept=text/event-stream`), browser HTTP JSON (`asty/web` parses via `JSON.parse`), `/metrics` (Prometheus text exposition is the standard wire format), `.asty`/`config.asty` (human-edited YAML).
- **No `codec` abstraction package exists.** `core/types/json.go` has only `MustJSON` (encode-only, swallows errors as `"{}"`). To change format anywhere, you touch ~30 call sites.
- **Leader entry has a dead format-migration branch** (`leader/election.go:84`, `leader/campaign.go` calls `parseLeaderID`) that handles "bare ID without IP" entries from older versions. Worth confirming no live deployment still carries those — if not, it's dead code.

## 2. High

### 2.1 `nats_writer.go` round-trip on every log line [+]

`asty/internal/features/observability/logs/nats_writer.go:25-46` is a zerolog `io.Writer` that:
1. Receives `p []byte` which is already a complete JSON log entry produced by zerolog (line 25).
2. `json.Unmarshal(p, &entry)` into `map[string]any` (line 31).
3. Adds `"timestamp"` if missing (line 35).
4. `json.Marshal(entry)` it back (line 39).
5. Publishes the result to NATS.

The unmarshal → map → marshal cycle is a pure CPU bill. zerolog supports hook patterns (`Hook` interface, `With().Int64("timestamp", ...)`) that would put timestamp into the struct *before* zerolog marshals. Alternative: if the input doesn't already contain `"timestamp"`, splice it in with a byte-level insert (`bytes.Replace`) without parsing.

**Cost per call:** one `json.Unmarshal` into `map[string]any` (reflection-heavy, allocates one map and N entries) plus one `json.Marshal` of the same map. On a node with ten chatty services this fires hundreds of times per second.

**Action:** **Variant 1** — drop the round-trip: configure zerolog's `TimestampUnix` hook so the timestamp is in the writer's input already; publish `p` verbatim. **Variant 2** — if some callers genuinely don't send `timestamp`, do a byte-level splice (`fmt.Appendf` of the closing `}` swap) instead of parse-then-marshal.

---

### 2.2 `core/types/commands.go` double-marshal envelope [+]

`asty/internal/core/types/commands.go:45-83` — every command (`MarshalStartCommand`, `MarshalRestartCommand`, `MarshalStopCommand`, `MarshalGetLogsCommand`) does:

```go
data, _ := json.Marshal(cmd)                                 // 1st pass
return json.Marshal(Command{Type: "start", Data: data})      // 2nd pass — re-walks `data`
```

`Command.Data` is `json.RawMessage` (line 11), so the inner bytes aren't re-escaped, but the outer `Marshal` still copies and validates them. Mirror cost on the receiver: `UnmarshalCommand` produces a `RawMessage`, then `Parse{Start,Stop,GetLogs}Command` does a second `Unmarshal` against it.

**Action:** **Variant 1** — collapse into one pass with a typed envelope per command (`type StartEnvelope struct { Type string; Service *ServiceDefinition }` — drop the discriminator dance entirely, use the NATS subject suffix as the type). **Variant 2** — keep `Command{Type, Data}` but make Marshal compose the JSON manually (one `fmt.Appendf` plus the inner marshal output). Variant 1 is cleaner unless the discriminator is genuinely needed at the byte level (it isn't — every consumer immediately switches on `cmd.Type`).

---

### 2.3 `agent/logstream.go` per-line `map[string]any` marshal [+]

`asty/internal/agent/logstream.go:54-57`:

```go
entry, err := json.Marshal(map[string]any{
    "line":      line,
    "timestamp": time.Now().Unix(),
})
```

Called once per process log line. `map[string]any` is the worst case for `encoding/json` — full reflection, two map iterations, sorted key emission. A typed struct `LogLine{Line string `json:"line"`; Timestamp int64 `json:"timestamp"`}` cuts the cost roughly in half even before any binary codec.

The same shape appears at `api/logs.go:104,122` and is partially mirrored in `server/logbuffer.go:50`. One typed struct dedupes all five sites.

**Action:** **Variant 1** — introduce `types.LogLine` (or `observability/logs.LogLine`, which already exists at `server/logbuffer.go:69` but is internal to that file) and use it everywhere a `{line, timestamp}` JSON shape is built or parsed. **Variant 2** — also stop parsing the log entry as `map[string]any` on the consumer side (see 2.4).

---

### 2.4 Consumer-side log reparse — `map[string]any` everywhere [+]

`asty/internal/server/logbuffer.go:50` (server, into log buffer) and `asty/internal/features/api/logs.go:96` (SSE streamer) both:

```go
var entry map[string]any
if err := json.Unmarshal(data, &entry); err != nil { ... }
level, _ := entry["level"].(string)
msg, _ := entry["message"].(string)
// timestamp via float64 type-assert
```

Same on the API logs path. Fully reflection-based, three type assertions, plus a `for k, v := range entry` loop in `formatLogEntry` to find unknown fields (`api/logs.go:62`).

**Action:** **Variant 1** — typed `zerologEntry struct { Level, Message, Time string; Timestamp int64; ... }` with `json.RawMessage` extra fields. **Variant 2** — emit timestamp from the producer as a number alongside the structured JSON already, and skip the parse on the consumer side (just split on the first `"` for level and pass the line through).

---

### 2.5 No `core/codec` abstraction — 64 direct `json.*` call sites [+]

`grep -rn "json\.Marshal\|json\.Unmarshal\|json\.RawMessage\|json\.NewEncoder\|json\.NewDecoder\|MustJSON" asty/internal/` returns 64 hits across 14 files. To change the wire format anywhere — even just to try `goccy/go-json` for benchmarks — you touch all of them.

This violates the project's stated stance: "helpers when the same shape repeats 3+ times" (`.claude/coding-rules/code-idioms.md:30`). `MustJSON` (`core/types/json.go`) is a half-step — it exists for the encode-only SSE path, but there's no symmetric decode helper and no way to swap implementation.

**Action:** **Variant 1** — introduce `asty/internal/core/codec` package with `Encode[T any](T) []byte`, `Decode[T any]([]byte) (T, error)`, default backend `encoding/json`. Migrate the ~30 producer sites to `codec.Encode`, consumer sites to `codec.Decode`. **Variant 2** — same, but split into `codec.Wire` (for pub/sub) and `codec.State` (for KV) so each can be swapped independently. Variant 2 is the architecturally cleaner path and the prerequisite for any future binary migration; Variant 1 is the smaller refactor that gives you the seam without prescribing where it leads.

---

### 2.6 Heartbeat and process-metrics are KV writes — no NATS publish [ ]

`asty/internal/agent/heartbeat.go:36-42` calls `clusterState.UpdateNode(info)`, which lands in `state/nodes.go:38` as `bucket.Put(key, data)`. Same for process metrics: `pushOneMetricsSample` (line 63) ends up at `state/allocations.go:127` as `bucket.Update(...)` via CAS.

This means "binary for heartbeats" = "binary for the entire cluster state of record". No middle ground unless heartbeat is moved to a NATS subject (e.g. `asty.v1.heartbeat.{nodeID}`) and a leader-side aggregator writes the KV record from the parsed bytes.

That decoupling is independently valuable:

- Heartbeat cadence becomes independent of KV write rate (currently every node writes KV every 5 s).
- KV format can stay human-readable (JSON for `nats kv get` debugging) while the wire is binary.
- One leader-side writer can batch and dedupe (e.g. drop a heartbeat that arrives within 50 ms of the previous one for the same node).
- Failure mode shifts: lose the leader and KV state freezes briefly until the new leader catches up; right now KV is always current but every node writes independently.

But it also adds: a NATS subscription on the leader, a fan-in goroutine, "what if the leader dies before flushing" reasoning. This is an architecture-level decision, not a one-task swap.

**Action:** discuss in execute mode before any code change. **Variant 1** — keep the coupling, leave heartbeat/metrics JSON, accept that binary stops at the KV boundary. **Variant 2** — decouple as above, ship binary heartbeat + JSON KV. **Variant 3** — full binary KV migration (covered separately in 3.1).

## 3. Medium

### 3.1 KV state format vs operator readability [ ]

KV-stored types — `NodeInfo`, `ServiceAllocation`, `ServiceCooldown`, `scaleOverride`, leader `Info` — are written/read as JSON across `state/{nodes,allocations,cooldowns,scale}.go` and `leader/{election,campaign}.go`. Marshal/unmarshal happens on every Put, every Get, every Watch event, every snapshot.

The trade-off is read-by-human. `nats kv get asty_nodes node.dev-1` showing JSON is genuinely useful during incident response. Switching to CBOR or MessagePack gains ~50% size and ~3× encode/decode speed but loses that. A debug command (`astyctl kv get`) decoding CBOR back to JSON for display would restore the operator path.

Not a defect on its own — depends on whether the operator workflow values raw `nats kv get` over a one-extra-step tooling decode.

**Action:** **Variant 1** — keep KV JSON; binary only for pub/sub. **Variant 2** — migrate KV to binary, add `astyctl debug kv` to decode for display. Pre-requisite is 2.5 (codec package). Don't decide without picking 2.6 first.

---

### 3.2 `MustJSON` swallows errors silently [ ]

`asty/internal/core/types/json.go:14-21` — on marshal failure it logs and returns `[]byte("{}")`. Used by SSE fan-out (`server/streamhub_pubsub.go:32` for events).

If an event ever fails to marshal, the UI gets a silent empty object. For events with no required fields this is fine; for events the UI keys on (e.g. `event.type`), it's invisible. The log line says it happened but nothing else fires.

**Action:** **Variant 1** — leave as is; SSE never blocks on individual events, an empty event is a no-op for the consumer. **Variant 2** — emit a `{"error": "marshal failed"}` sentinel so a downstream observer can flag it.

---

### 3.3 Leader entry legacy fallback — dead code? [ ]

`asty/internal/features/clustering/leader/election.go:82-86`:

```go
var info Info
if err := json.Unmarshal(entry.Value(), &info); err != nil {
    // Older versions stored the bare ID without IP; fall back to it.
    return Info{ID: string(entry.Value())}, nil
}
```

Same fallback in `parseLeaderID` (line 91-97). When was the "bare ID" format last written? If it was a pre-1.0 thing and no live cluster carries those entries, this is two dead branches.

The KV bucket has TTL 10 s (`leader/election.go:21`) so any leader entry older than 10 s is gone. Unless a cluster has been running uninterrupted since the format change, the legacy branch is unreachable. Worth a quick check before assuming.

**Action:** **Variant 1** — delete both fallback branches; if a legacy entry ever appears, the campaigner will fail to parse and re-elect on the next tick (which is the desired behaviour anyway). **Variant 2** — keep but add a `// TODO: remove after 2026-Q3` comment with the cluster-age assumption documented.

### 3.4 `gateway.metrics` payload is ad-hoc inline struct [ ]

`asty/internal/server/metrics.go:18-26`:

```go
var report struct {
    NodeID   string  `json:"node_id"`
    ValidRPS float64 `json:"valid_rps"`
}
```

Defined inline at the consumer with no producer-side counterpart visible (the gateway side that publishes to `asty.v1.metrics.gateway.*` isn't grep-visible in the asty package — likely lives in the gateway feature or a separate process). Two-field inline struct is fine for the size, but the producer/consumer aren't sharing a type — if either side changes a field, the other silently drops the value.

**Action:** **Variant 1** — promote to `types.GatewayMetricsReport` with both producer and consumer importing it. **Variant 2** — leave inline if confirmed that gateway and server share this only at the wire level intentionally (rare; usually wrong).

## 6. Not-defects

- **SSE / `/api/v1/*` JSON / `/metrics` text exposition** — flagged so it doesn't come up later. These are text-by-protocol or text-by-audience. SSE frames are `data: <utf8>\n\n`, browser parses with `JSON.parse`, Prometheus expects line-based text. No bytes there ever. Don't audit them.
- **`config.asty`, `.asty` files, `dev.vars`** — human-edited YAML/shell-env. Out of scope for serialization-format audit.
- **Demo services (`demo/internal/*`)** — they use NATS micro with their own JSON payloads; that's their design surface, not asty's. Mention only if the gateway grows knowledge of payload shapes (currently it just proxies bytes — `gateway/http.go`).
- **`MustJSON` returning `"{}"` on failure** — flagged as 3.2 because it's worth a sentence of discussion, but it's not a defect; it's a deliberate fail-soft for the SSE path.
- **The `goautoneg` indirect dep flagged in `project_goautoneg_known_oddity`** — known-OK, not part of this audit.

## 8. What's good

- **`json.RawMessage` in `Command.Data`** prevents the double-escape that a naive `Data []byte` field would cause. Inner payload bytes pass through the outer Marshal as-is. The remaining cost is just re-walking, not re-encoding.
- **`MustJSON` exists** — the SSE fan-out (`server/streamhub_pubsub.go:32`) and the `mustJSON` alias in `api/api.go:128` are the right pattern for "must-succeed marshal on a one-line call site". Good seam, even though only encode is covered.
- **All wire-format types live in `core/types`** with `json:""` tags consistent across the package. Adding a parallel `cbor:""` tag for a binary backend is mechanical.
- **NATS subjects follow a clean `asty.v1.<surface>.<...>` convention.** Wildcards (`asty.v1.agent.*.logs.*`) drive the consumer subscriptions cleanly. No format coupling to subject names — they're independent.
- **State Watch path is event-driven** (`state/watch.go`), with `watchKV` as the single driver. Per `concurrency.md:1`. Any codec swap touches the upsert/deleted decoders in one place per type (`nodeWatchHandlers`, `allocWatchHandlers`).
- **`gateway/http.go` proxies bytes opaquely** — it doesn't parse payloads, so demo-service format choices stay independent of asty's format decisions.
