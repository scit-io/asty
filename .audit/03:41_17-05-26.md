## 0. Summary

**Top-of-stack finding (§1.1)**: seven demo-service artefacts
leak into the platform code under `asty/`. Three places
hardcode the `api.v1.` NATS subject prefix (§2.8 was
incomplete — this audit found a third site). One Prometheus
Help string lies about its label cardinality and uses a
demo-shaped example (`auth`) as if it were an enum. The rest
are demo-shaped examples in comments and tests. Full list with
file:line in §1.1. (Demo-service mentions outside `asty/` —
`deploy/`, `Makefile`, coding-rule examples — are intentional
boilerplate per [[project-demo-boilerplate]], not findings.)

Direct answers to the user's four questions, then the broader
findings.

1. **Does `:8080/api/v1/` already cover everything `:8080/metrics`
   covers?** Not quite. `/metrics` exposes a few computations that
   `/api/v1/` does not surface today: cluster-wide absolute
   resource totals (CPU MHz, Memory MB, Disk MB, Swap MB — sums
   across all nodes), counts of nodes by disk class (SSD/HDD/
   unknown), per-allocation uptime in seconds, and `asty_leader`
   labelled by node ID. The data sources for these computations
   are all already in the snapshot — they're just not rendered into
   the JSON/SSE side. So the gap is computational/rendering, not
   data.
2. **Can `/metrics` be removed outright?** Not as-is. It has the
   only Prometheus-text rendering today, and the only renderings
   of cluster aggregates and alloc uptime. To remove it cleanly,
   those computations must move into the unified `/api/v1/`
   handlers, **and** the unified handlers must gain Prometheus-
   text content negotiation. After that, `/metrics` becomes
   redundant.
**Format note.** All three answers below assume the project's
binary-first rule
(`project_binary_first` in memory): every internal NATS/KV path
uses `codec.Wire`/`codec.State` (CBOR). JSON is allowed only on
five exit doors — HTTP, SSE, Prometheus text, logs, and the
dev-mode escape hatch. The unified route's three response forms
(SSE/JSON/Prom text) are all on those allowed exits, so the
rename does not regress format discipline. A separate finding
(§2.7) calls out one bug from a previous iteration that does
violate the rule on a NATS subject in scope.

3. **Can the unified route at `:8080/metrics` (replacing `/api/v1/`)
   serve dashboard SSE, CLI JSON, and Prometheus scrape?** Yes —
   technically. The implementation does not exist today;
   `accept.go` has only `wantsSSE`, and the GET handlers branch
   only between SSE and JSON. No handler emits Prometheus text in
   response to a per-resource path. The unified design needs a
   third negotiation branch and a per-resource Prometheus
   renderer.
4. **Does `:8081/metrics` (gateway) duplicate anything on
   `/api/v1/`?** No, and the relationship is not what the
   `gateway_*` name prefix suggests. Reading the labels and the
   increment call sites shows that **five of six counters
   describe user-facing services** (the `service` label values
   are demo / prod service names — xauth, xhttp, xws). These are
   the project's only production-traffic metrics (RPS, p95
   latency, error rate per service), and they were hiding on a
   per-node port behind names that read like sidecar internals.
   Two of the six are genuinely gateway-internal
   (`gateway_ws_connections_active`, the general-kind portion of
   `gateway_rate_limit_rejected_total`). User decision this
   turn: **delete `:8081/metrics` entirely**, relocate all six
   instruments to the orchestrator's unified surface via a NATS
   publication path, rename the four service-shaped ones to
   `asty_service_*`. See §2.4 and §5.F.
5. **Gateway path prefix today is hardcoded.** Two places —
   `gateway/routing.go:55` (literal `"v1"`) and `gateway/http.go:30`
   (NATS subject prefix `"api.v1.%s.%s"`). User wants the HTTP
   prefix configurable, default `/api/v1`. The NATS subject prefix
   is a separate concern (internal protocol) and can stay where
   it is. See §2.8 and §5.G.

Beyond the user's instructions, the audit surfaced:

6. **Doc-comment drift** at `features/api/api.go:20-23` claims
   three-way content negotiation already exists. The code in
   `accept.go` and the GET handlers only delivers two. This is a
   pre-existing **Critical** finding regardless of whether the
   unification ships — the comment lies to readers today.
7. **Inconsistency inside `/metrics`** — three `GaugeFunc`s in
   `prom.go:28-71` read `ClusterState()` directly; the six
   collectors read `streamHub.Snapshot()`. The same `/metrics`
   response can therefore reflect two slightly-different states
   under churn (snapshot is debounced 500 ms behind KV).
8. **Five GET routes are silently JSON-only** — no `wantsSSE`
   branch. List in §2.1.
9. **Mirror-rule violations on aggregates** — cluster absolute
   totals exist on `/metrics` but not on the SSE/JSON side
   (§1.4). Per-service surface has four different renderings
   each missing different subsets of the same struct (§2.2,
   re-counted against `ServiceWithUsage`: 13 fields, exposed as
   13/13 (SSE), 10/13 (autoscaler JSON), 6/13 (Prometheus), 0/13
   (`/services/{name}` JSON)). Per-allocation surface has
   similar drift (§2.5).
10. **JSON paths drift among themselves on data source.**
    `/nodes/{id}/allocations` reads the snapshot;
    `/services/{name}/allocations` reads KV directly. Same kind
    of inconsistency as §1.6 but inside the JSON family. See
    §2.6.
11. **One binary-first violation in scope** —
    `features/draining/wait.go:146` (§2.7). The only place where
    an internal NATS payload uses `json.Marshal` instead of
    `codec.Wire`. All other `json.*` sites in scope are on
    permitted boundaries (HTTP, SSE, Prometheus text, logs); the
    full grep is recorded in §2.7's tail.
12. **No Prometheus scrape config in the repo** under `deploy/`.
    The architectural decision to mirror UI ↔ Prometheus is in
    code only; the operator-side configuration to actually
    exercise it is left to whoever deploys.

## 1. Critical

### 1.1 Demo-service artefacts in `asty/` — must be excised entirely `[ ]`

Scope of this finding is **strictly `asty/`**, the platform's Go
package. Demo services (`demo/xauth`, `demo/xhttp`, `demo/xws`)
exist on purpose as reference workloads — their names must not
appear inside the platform code itself, but they remain in
`demo/`, in `deploy/{dev,prod}/`, in `Makefile`'s `build-demo`
target, and in coding-rule examples as **boilerplate** that the
customer of the system replaces with real services. See
[[project-demo-boilerplate]] for the exact split.

Re-verification across `asty/` (three passes with different
grep angles) found seven leakage points inside the platform.

**A. Misleading Help string on `gateway_rate_limit_rejected_total`
exposes demo-specific `auth` example as if it were an enum `[ ]`**

`features/gateway/metrics/metrics.go:55-63` declares:

```text
RateLimitRejectedTotal := promauto.NewCounterVec(
    prometheus.CounterOpts{
        Name: "gateway_rate_limit_rejected_total",
        Help: "HTTP requests rejected by Gateway rate limiter, by kind (general|auth).",
    },
    []string{"kind"},
)
```

The `kind` label takes two kinds of values at the increment
sites (`middleware.go:25,33`): the literal `"general"` (fallback)
and the **matched rule's prefix string** (which is whatever the
service declared in its `.asty` file). The values are not
"general or auth" — they're "general or any path prefix any
service declared". The Help string lies about cardinality and
treats the `auth` (xauth) prefix as a built-in value when it's
just the example that happens to exist in dev.

Action: rewrite the Help string to "by kind (`general` for the
fallback cap, otherwise the matched service rule's path
prefix)". Disappears anyway with §5.F.5 (the whole
`gateway/metrics/` package is dropped when `:8081/metrics` is
deleted), but the misleading text should not survive into the
unified surface either — when the four service-shaped counters
relocate to `asty_service_*`, the new Help text must be honest
about its label semantics from the start.

**B. Hardcoded `api.v1.` prefix in WebSocket subject `[ ]`**

`features/gateway/websocket.go:67`:

```text
baseSubject := fmt.Sprintf("api.v1.%s.ws", service)
```

Same class of defect as §2.8 (the HTTP path of `api.v1.` is
hardcoded in two places — `routing.go:55` and `http.go:30`).
This third site was missed in §2.8's enumeration. The fix is
identical: the NATS subject prefix is internal protocol; if
we ever decide to make it configurable too, all three sites
change together. For now §5.G's plan extends to cover
`websocket.go:67`.

**C. Test fixtures in platform packages use demo service names `[ ]`**

`asty/internal/features/scheduling/scheduler_test.go:62`,
`:93`, `:121` create test allocations with `Name: "xauth"` and
`Name: "xhttp"`. Tests should use generic names (`"svc-a"`,
`"test-service"`) so they don't read like they're testing demo
integration. Tests aren't supposed to encode knowledge of which
services exist.

Action: rename to neutral fixture names in those three sites.

**D. Test fixture in `artifact_test.go` hardcodes `xauth` artefact
URL `[ ]`**

`asty/internal/server/artifact_test.go:32-34` uses the

`https://github.com/${GITHUB_REPO}/releases/download/${VERSION}/xauth_linux_${ARCH}.tar.gz`.
The test verifies env substitution, but the example binary

**E. Comment in `draining/run.go` names xhttp `[ ]`**

`asty/internal/features/draining/run.go:80` — a comment reads

### 1.2 Doc-comment vs code drift on the API struct `[ ]`

`features/api/api.go:20-23` (verbatim):

> API provides the orchestrator's HTTP surface: SSE streams,
> polling endpoints, and command POSTs — all on a single port.
> **Content-negotiation per route picks the response form (JSON
> snapshot vs. SSE stream vs. Prometheus text) based on the Accept
> header.**

What the code actually does:

- `features/api/accept.go:9-17` has one helper, `wantsSSE`. It
  matches the substring `text/event-stream` only.
- No `wantsProm`/`wantsPrometheus`/similar exists anywhere in the
  repo (verified by `grep` on all `*.go`).
- Every GET handler I read (`handleCluster`, `handleNodes`,
  `handleNode`, `handleServices`, `handleService`, `handleAllocation`,
  `handleClusterLogs`, `handleNodeLogs`, `handleAllocationLogs`)
  branches `if wantsSSE(r) { stream } else { JSON }`. No third
  branch.
- Prometheus is served only by the separate path `/metrics` via
  `handleMetrics` (`features/api/status.go:68-70`).

So the comment promises three-way negotiation; the code delivers
two-way plus a separate path. The user's architectural goal this
turn is to make the comment true. Until then, the comment misleads
every reader.

**Action:** part of the unification plan. See §5.A.

### 1.3 No Prometheus content negotiation hook `[ ]`

The single missing piece for unification: `accept.go` does not
recognise Prometheus's content type
(`application/openmetrics-text` or `text/plain; version=0.0.4`).
Until it does, no GET handler can branch into a Prometheus
rendering.

The Prometheus library's own request-side helper is
`expfmt.Negotiate(r.Header)`, which returns a `Format` value the
library uses to pick the encoder. The unification plan needs a
similar branch (either pull in `expfmt.Negotiate` directly or
write a small `wantsProm` mirror of `wantsSSE`).

**Action:** §5.A.

### 1.4 Mirror-rule violation — cluster totals are on `/metrics` only `[ ]`

`prom_cluster.go:80-138` emits these gauges:

- `asty_cluster_cpu_total_mhz`, `asty_cluster_cpu_available_mhz`,
  `asty_cluster_cpu_used_mhz`
- `asty_cluster_memory_total_mb`, `_memory_available_mb`,
  `_memory_used_mb`
- `asty_cluster_disk_total_mb`, `_disk_available_mb`,
  `_disk_used_mb`
- `asty_cluster_disks_ssd`, `_disks_hdd`, `_disks_unknown`
- `asty_cluster_swap_total_mb`, `_swap_available_mb`,
  `_swap_used_mb`
- `asty_cluster_rps`, `asty_cluster_health_percent`
- `asty_leader{node_id=…}`

The SSE/JSON side at the same orchestrator port emits a much
shallower cluster status — `stream_cluster.go:69-85` (`emitStatus`
+ the `cluster_metrics` event) emits **only**
`cluster_metrics.cpu/memory/rps` as percentages and per-snapshot
points, plus `status.cluster.{leader, leader_ip, is_leader,
nodes_total, nodes_healthy}` and `services.loaded`. The JSON
snapshot for `/` (`status.go:42-53`, `fetchClusterJSON`) emits
exactly those same fields and nothing else.

Absolute totals (MHz, MB), disk-class counts, leader label as a
gauge — none of these reach the dashboard. The frontend ClusterStatus
type at `asty/web/src/types/index.ts:76-87` only declares
`leader, leader_ip, is_leader, nodes_total, nodes_healthy`.

This is the kind of asymmetry the mirror rule exists to prevent.
After unification the absolute totals belong in the snapshot view
the SPA reads too (whether the SPA *displays* them is a separate
question).

**Action:** add cluster aggregates to the snapshot/cluster JSON
response. The numbers are already computed in
`prom_cluster.go:86-105`; lift the loop into a helper used by
both renderers. See §5.B.

### 1.5 Per-allocation uptime is computed only for Prometheus `[ ]`

`prom_allocs.go:81-85` computes `uptime_seconds` per allocation:

```text
if !a.StartedAt.IsZero() && a.Status == types.AllocRunning {
    uptime = now.Sub(a.StartedAt).Seconds()
}
```

No counterpart in the JSON/SSE path. `allocations.go:27-39`
returns `*types.ServiceAllocation` as-is and the frontend
`Allocation` type (`web/src/types/index.ts:45-61`) carries
`started_at` but no derived uptime. The SPA must compute uptime
client-side from `started_at` if it wants to display it; today the
allocation overview pages don't expose it.

**Action:** lift the uptime computation into a shared helper and
emit on both surfaces, or document explicitly that the SPA
derives it locally. See §5.B.

### 1.6 `/metrics` itself is internally inconsistent on data source `[ ]`

In the same `/metrics` response three different data sources are
mixed:

- `prom.go:28-71` — three `GaugeFunc`s (`asty_cluster_nodes_total`,
  `asty_cluster_nodes_healthy`, `asty_cluster_services_loaded`)
  call `api.ctx.ClusterState().ListNodes()` /
  `api.ctx.Services()` **directly** on every scrape.
- `prom_cluster.go`, `prom_nodes.go`, `prom_allocs.go`,
  `prom_services.go`, `prom_nats.go` — five collectors call
  `c.api.ctx.StreamHub().Snapshot()` per scrape (verified at
  `prom_cluster.go:81`, `prom_nodes.go:91`, `prom_allocs.go:60`,
  `prom_services.go:50`, `prom_nats.go:82`).
- `prom_deploy.go:36-46` — reads `c.api.ctx.Deployer().GetHistory()`
  and dedupes per service.

`streamHub` is debounced 500 ms (`server/streamhub.go:13`,
`snapshotDebounce`). Under a burst of KV updates, the three
`GaugeFunc`s in `prom.go` see fresh data while the collectors see
snapshot data up to 500 ms stale. Within a single scrape the
`/metrics` output can therefore briefly disagree with itself —
`asty_cluster_nodes_total` (fresh) and the per-node rows from
`nodeCollector` (snapshot) can show inconsistent counts.

**Action:** unify on one source. Snapshot is the cheaper read and
the rest of the file already uses it; convert the three
`GaugeFunc`s to read from `StreamHub().Snapshot()`. Falls into
§5.C.

## 2. High

### 2.1 Five GET routes are silently JSON-only `[ ]`

GETs that DO content-negotiate (verified by reading each handler):
`handleCluster`, `handleClusterLogs`, `handleNodes`, `handleNode`,
`handleNodeLogs`, `handleAllocation`, `handleAllocationLogs`,
`handleServices`, `handleService`.

GETs that DO NOT (no `wantsSSE` call, no SSE branch):

- `handleNodeDrainStatus` (`nodes.go:138-158`) — drain progress.
  Streaming would be useful: a drain runs for minutes and
  operators may want to watch.
- `handleNodeAllocations` (`allocations.go:13-21`) — list of
  allocations on a node.
- `handleServiceAllocations` (`services.go:47-63`) — list of
  allocations of a service.
- `handleServiceAutoscaler` (`autoscaler.go:13-44`) — autoscaler
  status + events; clearly something users would want live.
- `handleServiceDeployHistory` (`services.go:182-196`) — deploy
  history (immutable past records, so streaming is debatable).

The asymmetry is jarring: `/services/{name}` streams, but
`/services/{name}/autoscaler` doesn't. `/nodes/{id}` streams, but
`/nodes/{id}/allocations` doesn't.

**Action:** during the unification, decide per route whether SSE
adds value. At minimum drain status and autoscaler should stream;
deploy history can stay polling-only. See §5.D.

### 2.2 Per-service surface is asymmetric across four renderings `[ ]`

The same conceptual data — what the dashboard's service page or
an operator wants to know — is rendered differently on every
surface. Re-counted by reading the struct and every emitter:

**`types.ServiceWithUsage`** (the canonical struct built in
`server/snapshot.go:142-185`) has **13 fields**:
`ServiceDefinition, CurrentCopies, AvgCPUPercent, AvgMemoryPercent,
AvgCPUMHz, AvgMemoryMB, MinCopies, TargetCPU, TargetMemory,
TrafficThreshold, CooldownUpActive, CooldownDownActive,
LastAction, LastActionAt`.

What each surface actually exposes:

| Surface | Code | Fields exposed |
|---|---|---:|
| `/services/{name}` JSON | `services.go:39-43` returns `{service: ServiceDefinition, allocations}` | 0 of 13 runtime fields (only the static definition) |
| `/services/{name}` SSE | `stream_service.go:43-46` emits `*ServiceWithUsage` | **13 / 13** |
| `/services/{name}/autoscaler` JSON | `autoscaler.go:31-43` builds a map | 10 of 13 (no `AvgCPUPercent`, `AvgMemoryPercent`, `AvgCPUMHz`, `AvgMemoryMB`) |
| `/metrics` (`asty_service_*`) | `prom_services.go:21-37` registers 6 descriptors | 6 of 13 (no `AvgMemoryPercent`, `AvgCPUMHz`, `TargetCPU`, `TargetMemory`, `TrafficThreshold`, `LastAction`, `LastActionAt`) |

So **four different renderings of the same data**, each missing
a different subset. The JSON snapshot of `/services/{name}`
misses ALL runtime data — the page that's most likely to be
polled by a CLI tool or external script gets the worst summary.

After unification (one path × three formats), the Prometheus
rendering needs to cover the seven currently-missing fields
(`TargetCPU/Memory/TrafficThreshold` as gauges,
`LastAction/LastActionAt` as a labelled gauge with state on the
label and the timestamp as the value, `AvgMemoryPercent`,
`AvgCPUMHz` as separate gauges), and the JSON path needs to
return `ServiceWithUsage` consistently.

**Action:** §5.B.

### 2.3 No Prometheus scrape configuration in the repo `[ ]`

`grep` of `deploy/**/*.{yml,yaml,conf}` for `metrics`/`prometheus`
returns nothing. Whoever deploys must wire the scrape themselves
pointing at `:8080/metrics` and `:8081/metrics`. The architectural

### 2.4 `:8081/metrics` is mislabelled — five of six counters are about user services, not about the gateway `[ ]`

**Earlier draft of this finding mis-read the data.** I called the
six counters "gateway operational counters" based on the
`gateway_*` / `nats_*` name prefixes. Reading the **labels**
instead of the names — which is what the data is actually about —
shows the opposite:

| Instrument | Labels | What the data actually describes |
|---|---|---|
| `gateway_http_requests_total` | `service, method, status` | RPS per **user service** (xauth, xhttp, xws…), broken down by API method and HTTP status |
| `gateway_http_request_duration_seconds` | `service, method` | Latency of **user services**, per method |
| `gateway_ws_connections_active` | — | Active WS sessions on the node (truly gateway-aggregate) |
| `gateway_rate_limit_rejected_total` | `kind` | Rejections, including per-service rate-limit rules |
| `nats_request_duration_seconds` | `service` | NATS round-trip to **user services** |
| `nats_request_attempts_total` | `service, outcome` | Attempts to **user services**, by outcome |

- These are the **only** production-observability metrics in the

  per-service info (copies, avg CPU/Memory) — but nothing about
  actual request traffic, latency, or error rate. The numbers
  operators need first when something breaks (RPS, p95 latency,
  5xx rate, per-service) are stuck on `:8081/metrics` with names
  that look like gateway internals.

- The naming actively misleads. An operator scraping the
  orchestrator's `:8080/metrics` reasonably assumes that's where
  service traffic metrics live. They don't — they're on the
  agent's port, behind a name that looks like sidecar stuff.

- The two genuinely gateway-internal instruments
  (`gateway_ws_connections_active`, the `general`-kind portion of
  `gateway_rate_limit_rejected_total`) are valid as-named. The
  other four should be **renamed** to `asty_service_*` so the
  data and the name agree.

User's instruction this turn — "all metrics on one route" — fits
this picture exactly: per-service traffic counters belong on the
unified observability surface alongside `asty_service_*`. They
should never have been hidden on a separate port labelled "gateway".

**Action:**

1. **Move** per-service counters
   (`gateway_http_requests_total`,
   `gateway_http_request_duration_seconds`,
   `nats_request_duration_seconds`,
   `nats_request_attempts_total`) to the unified
   orchestrator-side metrics surface. Rename to
   `asty_service_*` so the name describes the subject.
2. **Keep** the two genuine gateway-internal instruments
   (`gateway_ws_connections_active`,
   `gateway_rate_limit_rejected_total`) on `:8081/metrics`
   under their existing names — they really are about the
   gateway process.
3. **Aggregate** the moved counters cluster-wide on the
   orchestrator. Each agent's gateway already publishes
   ValidRPS over NATS to feed the autoscaler
   (`features/gateway/rpsreporter.go`); the same channel can
   carry the broader per-service stats, with the orchestrator
   maintaining a cluster-wide counter set.

See plan §5.F (re-written).

This finding subsumes my previous "two ports, same path scheme"
recommendation. That recommendation was wrong because it kept the
per-service metrics labelled as gateway internals on a separate
port. The correct move is to relocate them to the surface where

### 2.7 Binary-first violation — drain progress published as JSON on an internal NATS subject `[ ]`
<!-- (kept at 2.7 — surrounding sections renumbered to flow with the new finds 2.5, 2.6) -->

Project rule (`project_binary_first` in memory): every internal
NATS payload between Asty processes uses `codec.Wire` (CBOR in
production, JSON only in dev mode via `codec.UseJSONForDev`).
JSON is allowed only on five exit doors — HTTP responses, SSE
payloads, Prometheus text, logs, and the dev-mode escape hatch.

Grep of `json.Marshal`/`json.Unmarshal` against the metrics
scope found exactly one violation:

- **`features/draining/wait.go:146`** — `publishDrainEvent` marshals
  the drain status via `json.Marshal(status)` and publishes to
  `asty.v1.drain.progress`. Both ends are Asty (publisher: drain
  manager in the leader server; subscriber:
  `server/streamhub_run.go:18-22`, which fans the bytes out to
  SSE clients).

The data eventually reaches SSE clients (browsers parse JSON), so
the JSON encoding is convenient at the destination — but it
violates the rule at the source. Two acceptable resolutions:

1. **Strict fix.** Publisher uses `codec.Wire.Marshal`; the
   stream hub's drain subscriber decodes via `codec.Wire.Unmarshal`
   and re-encodes as JSON before fanout to SSE. Pays a small
   CPU cost on the receiver to honour the rule.
2. **Documented exception.** Subject moves to a "JSON-by-design,
   user-facing-bytes-only" category. This is the slippery
   slope — once exceptions appear, the rule erodes. Not
   recommended.

**Action:** option 1. See plan §5.H. Surfaces here because the
drain subject is on the metrics audit's path (it's part of the
state-streaming surface shared with `/api/v1/...`).

The same grep produced four other matches; all are on permitted
boundaries:

- `features/api/logs.go:63,97,115` — log SSE / display path.
  Allowed (SSE) and partially deprecated by the log audit.
- `agent/logstream.go:55` — wraps service stdout into LineFrame on
  NATS. Allowed (logs exception); also being removed in the log
  audit's phase A.
- `features/observability/logs/entry.go:44-58,84` — log decoder.
  Allowed (logs exception).

None of those are bugs by the binary-first rule.

   of the user's instruction but worth listing as the

## 8. What's good

- **Single `apiPrefix` constant on each side**, with comments on
  both Go and TypeScript flagging the manual-sync coupling.
  Without those comments the rename would silently break the SPA.
- **`StreamHub` interface in `context.go`** keeps the API package
  decoupled from the server package — cycles already prevented.
  The unification doesn't have to fight this.
- **Six collectors, six files, one per concern** under
  `prom_*.go`. Easy to lift into per-resource renderers because
  they're already split that way.
- **Snapshot is the right central concept.** Five of six
  collectors and every SSE emitter read it; making it the
  unified source after Phase B closes 1.5 and 3.5 for free.
- **Doc comments on each Prometheus instrument** include the
  matching UI label (e.g. `"asty_cluster_nodes_total" ...
  "(cluster.nodes_total in the UI)"`). Audit-friendly and the
  mirror rule's intent is visible even if today's code violates
  it in one place.
- **Frontend SPA already opens exactly one EventSource per page**
  (`store/cluster.ts:62-65`), so the unification on the SSE side
  is one rename, not a reshaping.
