## 0. Сводка верхнего уровня

Кодовая база очень аккуратная после Phase-6 рефакторинга: модули поделены по фичам,
размеры файлов под 200 строк, типизированные `*Status` enum'ы, документация в `doc.go`,
правила в `.claude/coding-rules/`. Найденные дефекты в основном — это:

1. **Дрейф документации vs реальности.** `CLAUDE.md` и `.claude/coding-rules/README.md`
   ссылаются на удалённые `dev-docs/*.md` (git status показывает 32 удалённых файла).
2. **Структурное расхождение dev/prod** в `deployments/envs/dev/*.asty` vs
   `deployments/infra/*.asty` (нет `replicas: 3`, разный `max_parallel`) — нарушает
   зафиксированное в памяти правило `dev_prod_sync`.
3. **Расхождение фронтов**: `asty/web/package.json` на актуальных мажорах (React 19,
   TS 6, Vite 8), а `demo/web/package.json` — на старых (React 18, TS 5, Vite 5).
   В одном репо два разных tooling-стека.
4. **Расхождение TS-типов с Go-типами** (`Node.status: 'initializing'`,
   `Allocation.status: 'stopping'` — таких enum'ов в Go нет).
5. **Кириллица в `demo/` коде** (`xauth/jwt.go`, `xws/manager.go`, `xws/session.go`).
   Язык проекта — английский, кириллицы быть не должно.
6. **N+1 запросы к KV** в `state.ListNodes` / `state.ListAllocations` — каждое перечисление
   делает `Keys() + Get(key)` поштучно.
7. **Мёртвые/недоделанные фичи**: proximity-валидация tcp-пингует порт `:4646` без
   слушателя; `sendUpdateCommand` шлёт `restart` агенту, у которого нет такого handler'а;
   `service scale`, `node pause`, `allocation restart/stop` отвечают 501.
8. **xws как сервис-обёртка над WS** — два уровня «session manager» (gateway/wssession
   + xws/session), 4 NATS-хопа на сообщение, состояние сессии в xws не переживает рестарт.
   См. секцию 2.21.

Никаких серьёзных дыр в логике планировщика, автоскейлера или gateway не найдено —
это солидно. Дальше — построчный разбор.

## 1. Критический приоритет

### 1.1. Расхождение фронтов: asty/web vs demo/web на разных мажорах [+]

Версии в `asty/web/package.json` и `demo/web/package.json` я перепроверил по
`registry.npmjs.org` — все существуют. Реальная проблема — **разрыв мажоров между
двумя фронтами в одном репо**:

| Пакет | `asty/web` | `demo/web` | Latest npm |
|---|---|---|---|
| `react` / `react-dom` | `^19.2.5` | `^18.3.1` | `19.2.6` |
| `typescript` | `~6.0.2` | `^5.6.3` | `6.0.3` |
| `vite` | `^8.0.10` | `^5.4.11` | `8.0.12` |
| `@vitejs/plugin-react` | `^6.0.1` | `^4.3.4` | `6.0.1` |
| `@types/react` | `^19.2.14` | `^18.3.12` | `19.2.14` |

Что это значит:

- `asty/web` — современный (React 19, Vite 8, TS 6).
- `demo/web` — отстал на полтора мажора по основным зависимостям.
- При попытке наладить общий tooling (shared components, общий типовой пакет,
  единый ESLint config) — несовместимо.

**Действия:**
- Либо подтянуть `demo/web` до того же стека, что и `asty/web` (риск: React 18→19
  meaningful migration; vite 5→8 — config breaking changes).
- Либо явно признать, что это две независимых SPA, и зафиксировать «demo/web
  заморожено на 18.x, обновлять только при существенных причинах».

Поправил после ошибки в первом проходе аудита, где я ошибочно утверждал, что версии
в `asty/web` не существуют. На самом деле существуют — проблема в дельте между фронтами.

### 1.2. dev/prod структурно разошлись в `.asty` [+]

Зафиксированное правило (`feedback_dev_prod_sync`): «никаких структурных расхождений между
окружениями». Сейчас:

- `deployments/envs/dev/xauth.asty` vs `deployments/infra/xauth.asty`:
  - dev: `kv.[0]` без `replicas` (используется auto). Prod: `replicas: 3`.
  - dev: `update.max_parallel: 2`. Prod: `update.max_parallel: 1`.
- `deployments/envs/dev/xhttp.asty` vs `deployments/infra/xhttp.asty` — то же самое
  (`replicas` и `max_parallel`).
- `deployments/envs/dev/xws.asty` vs `deployments/infra/xws.asty` — `max_parallel`.

Поведенческие отличия (`max_parallel`) допустимы как осознанный tradeoff, но
**структурное наличие/отсутствие поля** — нет. Решение: либо везде указать `replicas`
(в dev — `1`), либо выкинуть из обеих и доверять `autoReplicas()` (`server/kv.go:105`).

но в `asty/internal/core/types/node.go:16` enum `NodeStatus` его не содержит. Похоже,

### 1.5. Стираемые UI-эндпоинты возвращают 501 [+]

`asty/web/src/api/client.ts:28-74` ставит кнопки на действия, которых нет на сервере:

**Действия (любой из вариантов, выбрать осознанно):**
- Либо реализовать (хотя бы базовый рестарт = stop + start) и снять 501-ы.
- Либо удалить кнопки/эндпоинты из UI и `client.ts` до момента, когда руки дойдут.
  Текущее состояние («есть кнопка, но не работает») нарушает правило
  `.claude/coding-rules/clarity.md:30` «no dead stubs» / «501-over-fake-200».

### 1.6. Proximity validation шлёт TCP-ping в никуда [+]

`asty/internal/features/scheduling/proximity/validate.go:27` — `pingProbePort = ":4646"`.
`grep -rn "4646"` по всему репозиторию находит только это объявление константы.
Никакого `Listen(":4646")` в коде нет. `measureLatency` всегда падает в
`nodes1[0].IP == ""` или `pingNode` возвращает 0 на отказе `DialTimeout` — т.е.
валидация всегда сообщает «actual==0», ветка warning'а никогда не срабатывает.

**Действия:**
- Либо поднять lightweight TCP-listener в агенте на 4646 (и зарегистрировать его как
  именованную константу в `core/netutil`).
- Либо убрать всю валидацию: код в `proximity/validate.go` + горутина в `server/boot.go:112`.
  «Часовая фоновая проверка, которая всегда молчит» — типичный мёртвый код.

### 1.7. N+1 KV запросов в `state.ListNodes` / `state.ListAllocations` [+]

`asty/internal/features/clustering/state/nodes.go:66`,
`asty/internal/features/clustering/state/allocations.go:57-121`:

```go
keys, _ := bucket.Keys()
for _, key := range keys {
    entry, _ := bucket.Get(key) // RTT на каждый ключ
    json.Unmarshal(entry.Value(), ...)
}
```

При сотне аллокаций — сто round-trip'ов в JetStream. Эти функции дёргаются из
`scheduler.ReconcileService`, `controller.dispatchPending`, `controller.pruneFailed`,
`autoscaler.EvaluateService`, `api.handleAllocations`, `api.findAllocationByID`,
`api.nodeAllocCounts` — горячий путь.

**Действия (по нарастанию усилия):**
- Быстро — на API-стороне использовать `streamHub.Snapshot().AllocByID` /
  `AllocsByService` (уже построенные индексы в `server/snapshot.go`) вместо
  собственного перебора через `state`.
- Правильно — переключить `ListAllocations` на `bucket.Watch()` с пустым
  стартовым состоянием или однократный `bucket.History(...)`, либо собрать индекс в
  `state.ClusterState` (по аналогии с `allocIndex` в `server/snapshot.go`) и отдавать
  оттуда. Это снимет N round-trip'ов и улучшит latency `reconcile`.

### 1.8. Кириллица в коде `demo/` [+]

Заодно стале:
- `demo/internal/xws/manager.go:135` — «до Nomad SIGKILL по kill_timeout». Asty заменил
  Nomad (`CLAUDE.md:1-15`), упоминание Nomad — ложь.

В `xws/manager.go` особенно важно — там в логи попадают пользовательские события (open,
close), которые операторы будут грепать.

### 1.9. Deployer's rolling-update path silently broken [+]

Выпало из задачи 1.5: 4 UI-эндпоинта (scale/pause/restart/stop) реализованы, но
deploy-флоу остаётся сломанным end-to-end. Зафиксирую отдельной задачей.

**Что сломано:**
- `deployment/wait.go:sendUpdateCommand` шлёт NATS-команду `restart` с
  `{service_name, version}`.
- `agent/commands.go:39-49` не имеет handler'а для `restart` — возвращает
  «unknown command type».
- Поэтому при попытке деплоя rolling-update падает на первой же allocации.

**Связанные проблемы (выявились при разборе):**
- `types.ServiceDefinition` не имеет поля `Version` — версия живёт только на
  `ServiceAllocation`. Агент при `StartService` не знает, какую версию ставить.
- `artifacts/downloader.go` берёт URL как есть — шаблон `${VERSION}` в URL
  (`deploy/prod/xauth.asty:16`) не разворачивается, скачается буквальная строка.
- Существующий `StartService` при наличии процесса просто рефрешит alloc, не
  перезапускает — даже если deployer бы попросил.

**Минимальный план, чтобы deploy заработал:**
1. Добавить в `agent/commands.go` handler `restart`: парсит
   `{service_name, version}`, останавливает существующий процесс через
   `StopService`, обновляет `svc.Version` и заново стартует.
2. Расширить `ServiceDefinition` полем `Version` (или передавать версию в
   Start-command'е как отдельное поле).
3. В `artifacts/downloader.go` развернуть `${VERSION}`/`${ARCH}`/`${GITHUB_REPO}`
   через `os.ExpandEnv` или явную подстановку из плана деплоя.
4. Тест на rolling-update'е (хотя бы интеграционный с моком NATS).

Это полноценная функциональная задача, не косметика. Объём — ~день работы
с тестами.

### 2.6. Двойное ожидание health в `rolling.go` [+]

`asty/internal/features/deployment/rolling.go:47-54`:

```go
if !d.waitForBatchHealth(ctx, batch, plan) {       // уже ждёт MinHealthyTime
    return fmt.Errorf("batch update failed health check")
}
status.Updated += len(batch)
time.Sleep(plan.UpdateStrategy.MinHealthyTime)     // и здесь ждём ещё раз
```

`waitForBatchHealth` гарантирует, что батч был здоров `MinHealthyTime` подряд. Повторный
`Sleep` ничего не добавляет, кроме лишнего ожидания при больших окнах. Удалить либо
сократить до `time.Sleep(batchSpacing)` с отдельной константой, если идея была
«окно между батчами», а не «healthy time».

### 2.7. `process.GetLogs(lines int)` игнорирует параметр [+]

`asty/internal/features/execution/process/logs.go:56`:

```go
// TODO: replace with a true tail-N implementation ...
func (p *Process) GetLogs(lines int) ([]byte, error) {
    ...
    return io.ReadAll(f) // lines не используется
}
```

Параметр действительно не используется — вызывающий `agent/commands.go:126` сам режет
строки через `tailLines`. Это значит, что при огромном логе агент тащит в память **весь**
файл, чтобы отдать последние 100 строк. Реализовать backwards `os.ReadAt` по 4-KB кускам
или удалить параметр.

### 2.8. HTTP-загрузка без таймаута [+]

`asty/internal/features/deployment/artifacts/downloader.go:25-27`:

```go
return &Downloader{
    client: &http.Client{},  // нет таймаутов
}
```

Зависший CDN-сервер заставит агента ждать до OOM или агентского shutdown'а.
Поставить `Timeout: 5 * time.Minute` (типичный артефакт — десятки MB, минут хватит)
или явные таймауты на уровне `Transport` + per-request `context.WithTimeout`.

### 2.9. `time.Sleep` игнорирует контекст в restart loop [ ]

`asty/internal/agent/restart.go:94`:

```go
time.Sleep(svc.Restart.GetDelay())
```

Если в этот момент пришёл shutdown, агент будет ждать до 15 секунд (значение в
prod-конфиге). Заменить на `select { case <-ctx.Done(): return; case <-time.After(...): }`.

### 2.11. Stringly-typed actions нарушают правило типизированных enum'ов [ ]

### 2.19. Гонка при `drainOp.statusCopy` [ ]

`asty/internal/features/draining/manager.go:50-52`:

```go

    return op.status
}
```

### 2.21. Целесообразность xws как сервиса-обёртки над WS [ ]

**Архитектурный вопрос.** Сейчас цепочка сообщения от браузера до бизнес-логики
xws и обратно проходит так:

```
Browser ←─ WS ──→ Gateway (wsSession) ←─ NATS pub/sub ──→ xws (session)
            ↑                                                ↓
            └─────── NATS pub/sub ←─── (out subject) ────────┘
```

Это **4 NATS-хопа** на каждое сообщение. И при этом два уровня объекта «session»:

- `asty/internal/features/gateway/wssession.go:14-26` — обёртка над `gorilla/websocket.Conn`
  c `mu`, `ctx`, `cancel`, `wg`. **Оправдана** — без неё нельзя безопасно писать в
  Conn из нескольких горутин (Ping, NATS-callback, shutdown-горутина).
- `demo/internal/xws/session.go:33-43` — обёртка над NATS pub/sub, не над WS-Conn'ом.
  Хранит SID, in-subscription, inactivity-timer. **Дублирует часть функционала** wsSession:
  у обоих есть `mu`, `closed`-флаг, идемпотентный `close()`, idempotent timer-stop.

Что не так с xws как отдельным сервисом:

1. **State binding к процессу.** xws держит `m.sessions[sid]` в памяти. При рестарте
   xws (deploy, kill, OOM) все активные сессии теряются: gateway всё ещё держит WS
   с браузером, но `api.v1.xws.ws.in.{sid}` подписчиков больше нет — `ErrNoResponders`.
   Браузер не узнает, пока не отвалится по `wsReadDeadline=60s`.
2. **Нет реальной горизонтальной масштабируемости.** Queue Group `"xws"` распределяет
   только `connect`-сообщение. Дальнейший трафик SID_X идёт на тот xws-инстанс,
   который держит подписку `api.v1.xws.ws.in.SID_X`. Другие инстансы не подхватят
   SID после смерти первого.
3. **Inactivity timer дублируется.** Gateway уже выставляет `wsReadDeadline = 60s` на
   Conn (`gateway/gateway.go:29`), что и есть «закрыть, если клиент молчит». xws ставит
   независимый таймер по `X_WS_INACTIVITY_TIMEOUT = 3m` (`xws/config.go:26`). Два
   таймера на одну цель.
4. **SID-валидация дублируется.** `demo/cmd/xws/main.go:17` —
   `validSID = regexp.MustCompile("^[a-zA-Z0-9_-]{8,64}$")`. В gateway —
   `validSubjectToken = regexp.MustCompile("^[A-Za-z0-9_-]+$")` (`gateway/routing.go:13`).
   Регулярки разные, но цель одна.
5. **Накладные расходы.** На каждое client-message: serialize JSON → NATS publish →
   NATS dispatch → handler → NATS publish (echo) → NATS dispatch → gateway →
   `s.write` → gorilla. Один такт WS-сообщения = два круга через NATS dispatcher.

**Когда такая архитектура оправдана:**
- если xws **демонстрирует** паттерн «WS-сервис через NATS-мост» для будущих
  настоящих сервисов;
- если бизнес-логика xws нужна **за пределами** WS (например, та же сессия
  читается из xhttp по NATS request-reply).

Ни то, ни другое сейчас не выполняется — xws эхо-сервис в `demo/`, ни один другой
сервис в нём не нуждается.

**Возможные направления (выбрать осознанно):**

A. **Удалить xws как сервис.** Перенести логику open/close/echo прямо в gateway
   (`gateway/handleWS`). Минус: gateway перестаёт быть «протокольным мостом» — в нём
   появляется бизнес-логика. Плюс: -1 деплоимент, -2 NATS-хопа, -1 уровень session,
   -50% сложности.

B. **Сделать xws stateless.** Убрать `m.sessions` map, перенести inactivity tracking
   в gateway. xws превращается в чистый message handler по `api.v1.xws.ws.in.>`,
   который умеет отвечать в `api.v1.xws.ws.out.SID`. Минус: при рестарте xws пропадают
   только сообщения в полёте. Плюс: горизонтально масштабируем через queue group.

C. **Оставить как есть, но честно задокументировать.** В `xws.asty` написать
   «pattern reference for real services, do not use in prod with state».
   Минус: на новой команде кто-то скопирует и удивится.

Никакой автоматический рефакторинг здесь невозможен — это design call. Рекомендация
аудитора: B, потому что A теряет архитектурную инвариантность «gateway не знает о
бизнес-логике», а C — это `// here be dragons`-комментарий без устранения проблемы.

### 3.6. `keySuffix` — двусмысленное возвращаемое `""` [ ]

### 3.17. `gateway/ratelimit.go:108-117` `allowPath` — допустима путаница [ ]

```go
func (r *rateLimiter) allowPath(ip, path string) (allowed bool, matchedPrefix string)
```

Возвращает `(true, "")` если правило **не сматчилось** — но `(true, "rule")` если

Но семантика второго `bool` зависит от `prefix`. Чище — три состояния
(`Allow|Deny|NotMatched`) либо метод `matchedRule(path)` → `*pathRule`, а Allow
вызывать на нём.

`asty/internal/core/types/commands.go:32-36` — `LogsResponse` (агент → API).

### 3.19. `agent/restart.go:124-125` — двойной `Kill` [ ]


Сначала по group (`-pid`), потом по pid. Это идиоматично (groupkill ловит детей,

не вреден, но лишний. Удалить второй или прокомментировать «defense in depth».

`asty/internal/features/observability/events/buffer.go` и `logs/buffer.go` —
